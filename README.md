# Christopher

Keeps the ClickHouse schema for the CDC pipeline (MSSQL → Debezium → Kafka → ClickHouse)
versioned and applied through Liquibase.

This repo holds two things:

- **Schema**: every table, column, view and materialized view in ClickHouse, as Liquibase changesets.
- **Script history**: every data script run against ClickHouse, as run-once changesets.

GitHub has the text and review history. Liquibase's `DATABASECHANGELOG` table in ClickHouse
has the proof of what ran, where, and when. **Nothing changes ClickHouse schema except a
merged PR applied by GitHub Actions.**

## Layout

```
.
├── liquibase/
│   ├── changelog-master.yaml       # lists the databases IN ORDER (raw, analytics, direct)
│   └── <db>/                       # one folder per ClickHouse database (created automatically)
│       ├── changelog.yaml          # database.sql -> tables/ -> mvs/ -> scripts/ -> views/
│       ├── database.sql            # CREATE DATABASE <db> ...
│       ├── tables/<table>.sql      # CURRENT definition  ┐ generated by bin/export-schema.ps1,
│       ├── mvs/<mv>.sql            # CURRENT definition  │ never edited by hand
│       ├── views/<view>.sql        # CURRENT definition  ┘
│       └── scripts/<year>/         # EVERY change ever run, once each, in date order:
│                                   #   YYYY-MM-DD-NNN-<db>-<what>.sql
├── templates/                      # changeset + new-database templates
├── docker/liquibase/               # Liquibase + ClickHouse extension image
├── ops/clickhouse/                 # one-time bootstrap (users, grants) + audit queries
├── config/replicated-subset.yaml   # which MSSQL tables/columns go to ClickHouse
├── bin/                            # lb.ps1/lb.sh, new-changeset.sh, export-schema.ps1
└── .github/                        # plan on PR, apply on merge, image build, CODEOWNERS
```

**Two kinds of file:**

| | `tables/` `mvs/` `views/` | `scripts/<year>/` |
|---|---|---|
| holds | what each object looks like **now** | every change that was run, in order |
| written by | `bin/export-schema.ps1` (from ClickHouse) | you (`bin/new-changeset.sh`) |
| edit by hand | **never** | never after it ran; add a new script |
| Liquibase | `runOnChange`, `IF NOT EXISTS` / `OR REPLACE`: no-op on an existing db, builds the current shape on a fresh one | runs once, recorded with its rollback |

The one rule: **change things only with a script, then regenerate.** Editing `tables/x.sql` directly does nothing
(`IF NOT EXISTS`) and leaves the file lying about the database. CI rejects state-file changes without a new script.

Scripts must be safe on objects that are already current, because a fresh environment builds `tables/` first and then
runs every script: `IF [NOT] EXISTS`, preconditions with `onFail:MARK_RAN`. The templates do this.

## How a change flows

1. `bin/new-changeset.sh raw column appraisals region` -> `liquibase/raw/scripts/<year>/<date>-NNN-raw-appraisals-add-region.sql`. Edit it.
2. Preview locally: `.\bin\lb.ps1 update-sql --contexts=test`.
3. Open a PR. CI: header check, no edited/moved scripts, state files only with a script, `validate` + `update-sql` against test.
4. Merge. `liquibase-apply` runs `update` and tags the release with the **git short hash**.
5. `.\bin\export-schema.ps1` regenerates `tables/` `mvs/` `views/`; commit that (it will show e.g. the new column).

New database: it gets its folder automatically from `export-schema.ps1` (existing db, via `LB_DATABASES` in `.env`)
or `bin/new-changeset.sh <db> ...` (new db), and is appended to `changelog-master.yaml`. Then: move its include up if
something listed earlier depends on it, and grant the `liquibase` user on it.

## Point in time

- **See** the schema at any commit (nothing touches ClickHouse):
  `git show <hash>:liquibase/raw/tables/appraisals.sql`, or `git log -p -- liquibase/raw/tables/appraisals.sql` for its whole history.
- **Roll the database back** to a release (every apply is tagged with its git short hash):
  1. `.\bin\lb.ps1 rollback-sql --tag=<hash>`: preview the rollback blocks of every script after that release, newest first.
  2. `.\bin\lb.ps1 rollback --tag=<hash>`
  3. `git revert` the commits that added those scripts (otherwise the next `update` re-applies them), run
     `.\bin\export-schema.ps1`, commit.
  Rolling back drops what the scripts added: a dropped column's data is gone. Data scripts with `--rollback empty` are
  not undone. Review the preview.

### If an apply fails partway

| Fails at | State | Action |
|---|---|---|
| validate / status | nothing applied | fix in a new PR |
| update | earlier scripts applied + recorded; the failing one either not applied, or its DDL ran but wasn't recorded | fix the cause, re-run: preconditions + `IF [NOT] EXISTS` make it converge |
| tag | applied, release untagged | re-run; tagging is idempotent |

## Running Liquibase

Liquibase always runs in the container built from `docker/liquibase/Dockerfile`:

- Liquibase 4.33.0 + `liquibase-clickhouse` 0.8.3-arenadata (built from the tag) + clickhouse-jdbc 0.9.4. These are pinned together.
- The extension runs in single-node mode: its own tables (DATABASECHANGELOG, DATABASECHANGELOGLOCK_V1) are plain MergeTree in `raw`, the database in the JDBC URL.
  (Cluster mode would add `ON CLUSTER`, which the Replicated `default` database rejects. Never point the URL at `default`.)

### Local (inspection / planning only)

```bash
docker build -t christopher-liquibase:local docker/liquibase
cp .env.example .env               # fill in; .env is git-ignored
kubectl port-forward svc/<one-replica-service> 8123:8123 -n <ns>   # ONE replica, not the cluster service

bin/lb.sh status --verbose --contexts=test
bin/lb.sh update-sql --contexts=test
bin/lb.sh history
```

On Windows, use `.\bin\lb.ps1` with the same arguments, and set
`LIQUIBASE_COMMAND_URL=jdbc:clickhouse://host.docker.internal:8123/<db>` in `.env`.

Don't run `update` against shared environments from a laptop. Merging is the deploy.

## One-time setup

### ClickHouse (admin, once per environment)

Run `ops/clickhouse/001-bootstrap-database-and-users.sql` with the placeholders filled in. It:

- creates the `liquibase` ledger database and the `liquibase` user, the only user with DDL grants (on raw, analytics)
- creates the `cdc_sink` user (SELECT/INSERT only) and a `readonly` role

Also turn off auto-create and schema evolution in the sink connector.

### GitHub

1. **Self-hosted runner in AKS** (actions-runner-controller) with labels `self-hosted, aks`. It must be able to reach
   ClickHouse and pull from ACR.
2. **Image**: set repo variables `ACR_NAME`, `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`
   (an OIDC federated credential for this repo). Then run `build-liquibase-image`.
3. **Environments** `test-plan` and `test` (later `prod-plan` / `prod`, with required reviewers on `prod`). Each needs:

| name | kind | example |
|---|---|---|
| `LIQUIBASE_IMAGE` | var | `<acr>.azurecr.io/christopher-liquibase:4.33.0-0.8.3-arenadata` |
| `CH_JDBC_URL` | var | `jdbc:clickhouse://<replica-0-service>.<ns>.svc:8123/raw` |
| `CH_LIQUIBASE_USER` | var | `liquibase` |
| `LB_CONTEXTS` | var | `test` |
| `CH_LIQUIBASE_PASSWORD` | secret | from your secret store |

4. **Branch protection on `main`**: PR required, 1+ approval, `lint` and `plan` must pass. Turn on CODEOWNERS review
   and replace the placeholder teams in `.github/CODEOWNERS`.

## Bringing a database under Liquibase (from scratch)

```powershell
.\bin\export-schema.ps1                          # LB_DATABASES from .env -> liquibase\<db>\tables|mvs|views
.\bin\lb.ps1 validate
.\bin\lb.ps1 changelog-sync --contexts=test      # record everything as applied, executes nothing
.\bin\lb.ps1 tag --tag=<git short hash>
```

## Audit / paper trail

`ops/clickhouse/003-ledger-queries.sql` has queries for:

- everything applied
- data scripts that ran
- what each run applied
- replicas whose schema differs (missed DDL)

`ops/clickhouse/002-out-of-band-ddl-check.sql` finds DDL sent by anyone other than `liquibase`.

## Known limits (liquibase-clickhouse)

See `docs/liquibase-clickhouse.md` in the Christopher project for the full notes. In short:

- Only `update`, `tag` and `rollback` with hand-written SQL are supported. There's no `diff`, `generate-changelog` or auto-rollback.
- The Liquibase lock isn't atomic. The workflow `concurrency` group is the real lock.
- Always connect to one fixed replica, because Liquibase's own tables replicate with lag.
